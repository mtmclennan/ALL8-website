# ALL8 technical SEO and indexing audit

**November 20, 2026 · Production `https://all8webworks.com` · Repository baseline `e0db4d5`**

No technical indexing blocker was confirmed on the nine priority URLs. Each returned HTTP 200 with distinct titles, descriptions and H1s, crawlable navigation, primary content in the initial HTML, one matching canonical and Open Graph URL, and no indexing restriction in the sampled HTML or headers. The entire production sitemap contained 37 unique URLs that returned 200 and matched their page canonicals. The observed redirect chains and SEO signal inconsistencies warrant cleanup. Their effect on Google's reported exclusions is unverified.

Google Search Console status and the previous lack of a Change of Address submission were supplied by the site owner. Google Search Console, PM2, Nginx and the Cloudflare account were outside this audit's direct access. Public GET requests included a second pass on the nine priority pages with a Googlebot user-agent string. That checks user-agent-dependent responses from this network. URL Inspection and verified Googlebot logs are needed for Google's actual fetches and indexing decisions. [Google Page indexing report](https://support.google.com/webmasters/answer/7440203)

## Findings and severity

| Issue | Evidence | Severity and confidence | Fix and expected effect |
| --- | --- | --- | --- |
| HTTP, trailing slash and retired path variants add migration hops | Live `http://all8webworks.ca/pricing` first redirects to HTTPS on the same host, then to `.com/pricing`. HTTP on the other sampled alternate hosts also upgraded the protocol first. HTTPS on both `.ca` hosts and `www.all8webworks.com` sends canonical paths to the apex in one 301 and preserves queries. `.ca/pricing/` hits the apex with the slash and then a 308. Retired service and article slugs land on the same path at the apex before their Next.js 308 or 301. The sampled chains kept their mapping and showed no loop. Repo fallbacks are in [proxy.ts](../proxy.ts#L7) and [permanent-redirects.mjs](../config/permanent-redirects.mjs#L8). | **Medium, proven live.** The cause of Google exclusions is unverified. | Owner action in Cloudflare. Send alternate host and protocol traffic directly to the final apex path. Preserve query strings and applicable retired-path mappings. This reduces intermediate fetches and simplifies consolidation. [Google site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes) |
| Build and runtime production flags can disagree | [PM2](../deploy/pm2/ecosystem.config.cjs#L21) sets `DEPLOYMENT_ENV=production` when started with `--env production`. [Root metadata](../app/layout.tsx#L30) and prerendered HTML evaluate during the build. [Robots](../app/robots.ts#L5) is dynamic and evaluates at request time. The live sample permitted Googlebot and contained no production noindex. Deployment environment and historical artifacts were unverified. | **High impact if triggered, precondition proven in code.** Current production failure unverified. | Build and run production from the same explicit deployment environment. Confirm the artifact and worker independently. This prevents a preview build from serving noindex under a production process. |
| A page can override the preview noindex inherited from the root | The page helper set the robots key to undefined for ordinary pages. Next.js processes a provided robots key as a replacement. A direct child declaration can also replace the preview nofollow. CI intentionally uses `DEPLOYMENT_ENV=test`. See [metadata helper](../lib/seo/metadata.ts#L10), [legal page metadata](../app/(site)/legal/%5Bslug%5D/page.tsx#L44) and [CI](../.github/workflows/ci.yml#L20). | **Medium, proven at the metadata merge.** Preview exposure is unverified. | Applied the same policy in root and page metadata. Preview retains `noindex,nofollow` and deny-all robots. Production keeps intentional exclusions such as Hire Matt, legal pages, thin archives and CMS noindex posts. Prefer authenticated previews for access control. |
| A CMS canonical override can conflict with the sitemap and article schema | Previously, [article metadata](../app/(site)/blog/%5Bslug%5D/page.tsx#L54) accepted same-origin overrides while [sitemap](../app/sitemap.ts#L58) and [article JSON-LD](../app/(site)/blog/_components/ArticleJsonLd.tsx#L48) used the route slug. An override could also point to a known redirect or slash variant. All 37 sampled sitemap canonicals were consistent on production. | **Medium, proven code path with an override.** Active production conflict unverified. | Metadata, Open Graph, article schema and sitemap now use the same canonical calculation. The sitemap excludes alternate URLs and does not add arbitrary CMS override destinations. Known slug migrations retain precedence. Validate any deliberate CMS override's target with a GET and URL Inspection. [Google canonical signals](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) |
| Sitemap and schema used technical timestamps as content dates | Production XML had 17 dated entries. For example, `/blog/category/seo` claimed November 20, 2025 while its listings now include later posts. The previous [sitemap](../app/sitemap.ts#L58) used Sanity document timestamps for posts and categories. [The article template](../app/(site)/blog/%5Bslug%5D/BlogPost.tsx#L71) displays an explicit editorial update only. | **Low, proven in code and live XML.** Indexing effect unverified. | Use the visible editorial update date for sitemap and article schema. Use the valid publication date for initial sitemap freshness. Omit archive dates because the category document alone cannot date changes to its post list. Undated static entries remain undated. Google ignores `priority` and `changefreq`. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) |
| Site-wide schema required JavaScript and used a deprecated business type | Initial HTML included parseable route-level JSON-LD, including the three BlogPosting blocks. The site-wide nodes used `next/script` with `afterInteractive` in [the root layout](../app/layout.tsx), so they were absent as JSON-LD script elements in raw HTML. The [business record](../data/schema/organization.schema.json) used deprecated `ProfessionalService` and specified `serviceType`, a property for `Service` nodes. | **Low, proven live and in code.** | Emit the nodes in server HTML, escape script content, and use `Organization` with its supported properties. Keep the original organization ID so consumers can resolve publisher references without hydration. [ProfessionalService](https://schema.org/ProfessionalService) · [serviceType](https://schema.org/serviceType) |
| Multiple cache layers can delay changes to SEO signals | [Sanity's client](../app/studio/sanity/lib/client.ts#L5) uses its API CDN. Next ISR is hourly for [blog](../app/(site)/blog/%5Bslug%5D/page.tsx#L33) and [sitemap](../app/sitemap.ts#L16), daily for [service details](../app/(site)/services/%5Bslug%5D/page.tsx#L20). Home resources have an hourly fetch. [Example Nginx](../deploy/nginx/all8-tunnel.conf.example#L50) disables its proxy cache. Cloudflare reported `DYNAMIC` for sampled HTML/XML, while Next showed `HIT` and occasional `STALE`. Public robots had `max-age=14400` and Cloudflare-managed additions. Two sampled Next CSS/JS assets returned 200 with immutable caching. | **Medium if drift persists, cache behavior proven.** Incorrect cached metadata and deployed cache rules unverified. | Keep caching. After an SEO edit, compare the Sanity source, origin response and edge response after ISR has had a chance to regenerate. Investigate persistent differences before changing Sanity API CDN or edge policy. Purge only affected entries if the edge is serving obsolete directives. [Sanity API CDN](https://www.sanity.io/docs/content-lake/api-cdn) |
| Cloudflare-obfuscated email placeholder is a 404 in raw link checks | Raw HTML included `/cdn-cgi/l/email-protection`, which returned 404 by direct GET. It is a Cloudflare email placeholder and did not appear in the sitemap. Every sitemap URL had an incoming link in the sampled site crawl. No other same-origin link target tested from those pages returned an error. | **Low, proven live.** | Verify browser email decoding separately if the contact link fails for visitors. No change to public page discovery is needed for this placeholder. |
| Change of Address had not been submitted when the issue was reported | Owner-supplied state. Live sampled HTTPS migrations worked, and the owner reported that Google indexed an article. | **Medium, owner-reported.** Contribution to exclusions unverified. | When both properties and redirect coverage are verified, the owner can submit the permanent domain move from the old property. This communicates the move independently of per-URL indexing decisions. [Change of Address requirements](https://support.google.com/webmasters/answer/9370220) |

## Production and Search Console handoff

1. On the DigitalOcean host, identify the running worker under the PM2 owner with `pm2 describe all8-webworks`. The intended launch is `pm2 startOrReload deploy/pm2/ecosystem.config.cjs --env production`. Check the actual working directory and release and verify both build and runtime had `DEPLOYMENT_ENV=production`. For runtime, use `pm2 env <PM2_ID> | grep -E '^(DEPLOYMENT_ENV|NODE_ENV):'` and avoid dumping environment secrets. The runtime value alone does not verify an artifact's build flag. See [infrastructure cutover plan](infrastructure-cutover-plan.md).
2. Compare GETs for `/robots.txt`, `/sitemap.xml`, `/pricing` and one affected article on local Nginx and the public edge, using the same production Host. Compare status, HTML robots, X-Robots-Tag, canonical, Cache-Control, Age, CF-Cache-Status, Vary and X-Nextjs-Cache. Check the active Nginx/Cloudflare rules and bot events. Verify verified Googlebot requests in logs around the dates from URL Inspection. [Google crawler verification](https://developers.google.com/search/docs/crawling-indexing/verifying-googlebot)
3. In Search Console, export the indexing report and inspect the nine final URLs, plus an indexed control and representative old URLs. Record Google-selected canonical, user canonical, last crawl, referring pages or sitemap, crawl/fetch status and live rendered HTML. Use the live test for current eligibility, and the indexed result for Google's stored state. Check both properties before submitting Change of Address from the old property. Keep legacy redirects available for at least a year. [Google site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

## Post-deployment checklist

- Build with `DEPLOYMENT_ENV=production` and use the matching launch environment. Compare the origin and edge from the preceding handoff before drawing conclusions from the new release.
- Run `node scripts/verify-seo.mjs https://all8webworks.com` for the production sitemap, raw metadata, headings, JSON-LD, three same-host redirects and intentional noindex. To test a separately built preview, run `node scripts/verify-seo.mjs http://127.0.0.1:3000 --preview`.
- Recheck HTTP and HTTPS variants on `.ca`, `www.ca`, `www.com`, and the apex. Use a representative pricing and article URL, a retired alias and a slash variant with a query. Record every Location and the final 200. Check that Search Console's sitemap fetch succeeds and only submit the canonical sitemap for the new site.
- Verify HTML and Googlebot live results for the affected pages. If Search Console shows a materially changed priority page is eligible, request indexing once for a small sample. Track subsequent crawls and index outcomes in the report. [Request recrawling](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl)
